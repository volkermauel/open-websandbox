# Research notes — issue #134 "Container Snapshot"

Scratch evidence log for the feasibility verdict. Everything below was verified
during the investigation (2026-08-15); links included. Final deliverables:
issue comment on #134 + `docs/container-snapshots.md`.

## 1. What the upstream Snapshot feature actually is

- Docs: https://agent-sandbox.sigs.k8s.io/docs/sandbox/snapshots/
- It is **not** controller functionality. It is a **Python-SDK-only extension**:
  `PodSnapshotSandboxClient` / `SandboxWithSnapshotSupport` / `SnapshotEngine` in
  `clients/python/agentic-sandbox-client/k8s_agent_sandbox/gke_extensions/snapshots/`.
- Mechanism: the client creates **`PodSnapshotManualTrigger`** custom resources in
  the **`podsnapshot.gke.io`** API group. GKE's node agent + control-plane
  controller react, run gVisor checkpoint, store the snapshot in **Cloud Storage**,
  and surface a **`PodSnapshot`** CR. `suspend()` = snapshot + set the Sandbox CR's
  `spec.operatingMode: Suspended`; `resume()` = set back to `Running`, GKE restores
  the pod from the latest snapshot.
- The docs page itself states: "Snapshot/suspend/resume support is Python-only for
  now. `PodSnapshotSandboxClient` drives this through **GKE's `podsnapshot.gke.io`
  custom resources**, which the published Go SDK doesn't wrap."
- Prereq per docs: **GKE Autopilot cluster with gVisor node pool**.

## 2. Version status vs. our vendored upstream

- Our vendored controller: `open-websandbox-platform/upstream/VERSION` = **v0.5.3**.
  `grep -i snapshot sandbox-with-extensions-v0.5.3.yaml` → **zero hits**. The CRD
  does have `operatingMode` (line 460) — that's the generic park/resume field our
  reaper already uses.
- The Python snapshots extension **already exists at the v0.5.3 tag** (GitHub
  contents API, `gke_extensions?ref=v0.5.3` → `snapshots/` dir present). So the
  feature "was in" our pin — it's just GKE-only client code.
- Upstream releases: v0.5.4 (2026-07-30), v0.5.5 (2026-08-13). Grep of upstream
  repo for `podsnapshot` matches **only** Python client files + site docs — **no Go
  controller code in any release**. Re-vendoring to v0.5.4/v0.5.5 changes nothing
  for snapshots.
- Conclusion: there is **nothing to re-vendor**; the gap is not controller version.

## 3. GKE Pod Snapshots mechanism (what's underneath)

- Concepts: https://cloud.google.com/kubernetes-engine/docs/concepts/pod-snapshots
- Contents: **full application state** (all open FDs, threads, CPU registers,
  memory), container rootfs, **EmptyDir volumes**, tmpfs mounts. **PVs are NOT
  checkpointed.**
- Networking on restore: loopback connections, **listening sockets**, UDS survive;
  **external connections are terminated**; new pod IP; new hostname; wall-clock
  jumps ahead; env vars baked into memory can't be rewritten (read fresh ones from
  `/proc/gvisor/spec_environ`).
- Compatibility (whole-pod scope): distilled pod-spec hash must match, same
  machine series + CPU arch, same gVisor kernel version. rootfs-only scope is
  relaxed (no memory → no hw constraints).
- Storage: **Cloud Storage buckets only** (`PodSnapshotStorageConfig`).
- Limitations: "Pods must run in GKE Sandbox because Pod snapshots depend on the
  gVisor container runtime that GKE Sandbox provides." → the node agent +
  control-plane controller are **GKE-internal, closed-source plumbing**.

## 4. gVisor runsc checkpoint/restore on plain k8s (the open core)

- User guide: https://gvisor.dev/docs/user_guide/checkpoint_restore/
  (in-repo: `g3doc/user_guide/checkpoint_restore.md` — **verified present on our
  pinned `release-20260727.0` branch**, incl. the Application-Driven section).
- Core CLI: `runsc checkpoint --image-path=<dir> [--leave-running]`,
  `runsc restore --image-path=<dir>`; state files = `checkpoint.img`,
  `pages.img` etc. Options: `--compression` (none|flate-best-speed),
  `--exclude-committed-zero-pages`, `--direct` (O_DIRECT), `--background`
  (lazy page-in on restore — GKE's "background streaming" is this).
- Platform: C/R is sentry userspace state serialization — **no platform
  restriction documented; works under systrap** (no /dev/kvm involved).
- CPU compat: restore verifies target CPU features ⊇ checkpoint-time features;
  pin with `dev.gvisor.internal.cpufeatures` annotation for heterogeneous pools.
- Networking flags in our pin's `runsc/config/config.go` (verified on the release
  branch): `net-disconnect-ok`, `allow-connected-on-save`, `allow-live-tcp-migration`,
  `restore-spec-validation`.
- **Application-driven C/R** (landed June 22–23 2026, PiperOrigin-RevId
  935903198 / 936770245 → in `release-20260727.0`): root-container OCI annotations
  `dev.gvisor.internal.checkpoint.path` + `.enable=true` (+ `resume`, `compression`,
  `direct`, `exclude-committed-zero-pages`, `cuda-checkpoint-path`,
  `save-restore-exec-argv/timeou`); the workload writes `1` to
  `/proc/gvisor/checkpoint` and reads `resume|restore|error`. Destination is a
  local dir (or GCS via checkpoint gofer). → **an in-sandbox trigger with no node
  socket access needed**.

## 5. The orchestration gaps on plain k8s (blockers)

- **gVisor containerd shim**: `Checkpoint` Task API is a **stub returning
  `errdefs.ErrNotImplemented`** in our pin (`pkg/shim/v1/runsc/service.go`,
  verified on `release-20260727.0`). The implementing PR
  **google/gvisor#13326 "shim/runsc: support containerd checkpoint restore" is
  OPEN, not merged** (API check 2026-08-15: `"state": "open", "merged": false`,
  +829/−3, 10 files, last updated 2026-06-30). It would add:
  - shim `Checkpoint` → `runsc checkpoint --image-path --leave-running`;
  - restore control annotations `dev.gvisor.internal.restore.host-image-path`
    (+ `.direct`, `checkpoint.save-restore-exec-*`);
  - `Start` dispatch to `runsc restore` when the annotation + host path exist;
  - pod-restore ordering (sandbox/root container first).
- **containerd CRI**: `CheckpointContainer` not implemented for gVisor —
  containerd/containerd#12280 (open). kubelet `/checkpoint` API
  (KEP-2008, `ContainerCheckpoint` beta since k8s 1.30) is the *forensic* path
  and only works where containerd CRI → runtime shim support exists (runc/CRIU).
- **Kubernetes restore API**: does not exist at all (KEP-2008 restore phase
  deferred); restore must ride on runtime-level mechanisms (annotation-driven
  shim restore once #13326 lands).
- **runc/CRIU**: works only as privileged forensic checkpoint (CRIU binary on
  node, CAP_CHECKPOINT_RESTORE, kernel-version sensitive); no CRI restore path in
  k8s. Not our path — production is gVisor.

## 6. Our environment fit (verified in-repo)

- runsc pin `release-20260727.0` (infra/gvisor) — core C/R + app-driven C/R in;
  shim C/R out (see §5).
- Sandbox pods are **single-container** (chart `sandboxtemplate.yaml` → one
  runtime container) → whole-sandbox gVisor C/R granularity fits.
- Broker `resolve.rs`: deterministic sandbox name, polls `Ready` + **pod IP per
  resolution** → a restored pod (new IP) is picked up transparently. WS terminals
  are long-lived conns → **drop on restore**, clients reconnect (#135 scrollback
  flush helps).
- Persistent profile: RWX PVC — **PVs are never part of a container snapshot**
  (GKE same); files persist anyway → C/R is purely additive (memory+rootfs).
- Ephemeral profile: emptyDir/tmpfs **is** captured by runsc C/R → memory-state
  suspend becomes possible without a PVC.
- Node pool: dedicated homogeneous gvisor workers (`sandbox.open-websandbox.dev/type=sandbox`)
  → CPU-feature + machine compat OK; uniform runsc release pin handles gVisor
  version compat.
- Storage for state files: S3 machinery from #52 (`rust/runtime/src/snapshot.rs`,
  `rust/broker/src/s3.rs`) can be extended to a second artifact type.
- KIND e2e (kindest/node v1.31, containerd): gVisor C/R e2e possible via
  `scripts/setup-kind-gvisor.sh`; gVisor itself carries k8s C/R tests upstream.

## 7. Relationship to existing features

- **S3 workspace snapshots (#52)**: files-only, runtime-agnostic (runc+gVisor),
  profile-gated. Container snapshots: memory+rootfs+emptyDir, gVisor-only.
  → **complement**, not replace.
- **Park/resume (operatingMode Suspended)**: files-on-PVC scale-to-zero. C/R adds
  the missing memory dimension. Same lifecycle entry point.
- **Warm pool**: pre-provisioning optimization; orthogonal (C/R even threatens the
  warm-pool value prop for long-init workloads — but ours are shells, not models).
- **#130 (120s-suspend/long sessions)**: directly the beneficiary — today a parked
  session loses processes/package-layer state; C/R would close that.
